# Verification

All tests use disposable fixtures: a temporary data directory, a copied auth library with its own test accounts, no production traffic and no network (a build fetches its dependencies; a test never does). During development run focused checks; run the full lists below once, at the end. In a worktree set `TASKMIND_TEST_SITE_LIB=<seancheren-site>/lib` and `COREMIND_REPO=<CoreMind>`.

- `npm test` = `typecheck`, `check:limits`, `test:core`, `test:server`, `test:deploy`:
  - `check:limits`: `server/lib/limits.php` equals what `tools/gen-limits.mjs` writes from `model.ts` (caps, roles, the matrix, the id shape, error statuses; regenerate with `node tools/gen-limits.mjs`, never by hand).
  - `test:core`: vitest, `packages/core/test` (the model's constants and the interim page's caps and words, the matrix by role: viewers, members, admins, owners, private projects, member and ownership rules; which screen a first answer leads to, names and initials) plus `app/**/*.test.ts` (the 45 s request wait and the release stamp of every answer (`api`), the release watch (`release`), the session watch: closes on 401 or 403, leaves the page alone when a read fails, reloads on a new release, asks no more once closed (`watch`), theme names and variables and AA contrast of the shell's text in all four themes (`colors`)); then the atomic-storage check.
  - `test:server`: `server/tools/test.php` runs `server/tools/cases/*.php` (`errors`: every status and code agree with the generated table; `store`: round trip, a private file, fail-closed reads of junk, a flipped bit, another store's bytes and a lost key, the `workspace.version` marker, the one-time backup of a version bump and a different backup refusing the write; `concurrency`: six processes writing at once, none lost; `login`: the sign-in limiter and the address it counts, the per-account and app-wide caps (any number of addresses, the answer of a wrong password, fixed windows, fail closed, racing processes) and `tm_login()` end to end; `team`: the seed team and `taskmind_owners`, how a stored workspace is read into members, the gate for a member, a non-member, a removal, a demotion and an unreadable workspace, a fresh install seeded explicitly and once (six racing first requests, one log line) while a workspace that is missing after it existed, empty, damaged (not a store, cut short, no team, the team not a list) or undecryptable (a flipped bit, another key, a lost key) admits only a 503 for the seed owners and writes nothing, the session reply, the release stamp and host instance, and that `index.php` and `api.php` repeat the stamp pattern the lib states; `gate`: the real `api.php` and `bootstrap.php` under php-cgi against a stub of the site's account library: 401 signed out, 403 for an account off the team or one that no longer exists, `{ok, me, role, name, csrf, theme}` for members, the next request after a removal, GET and POST behind the gate, an unreadable, empty or lost workspace); `session`: the real `index.php` and `api.php` under php-cgi with real PHP session files and a carried cookie: a sign-in or sign-out with no token, an empty, wrong or cut-short one, another session's, the token from before sign-in, or the right one from another origin or cross-site is 403 and writes nothing (session files, ledger and workspace hashed before and after); the session id rotates at sign-in (old id 401, new CSRF token) and at sign-out (the signed-in id and the new one both 401), an unknown id is never adopted, and a member removed from the team is refused on the next request of the session they hold, then let in again when added back) through `harness.php`; then `staging-test.php`. One file: `node tools/php.mjs server/tools/test.php <part-of-name>`.
  - `test:deploy`: `tools/deploy.sh` (and the `dtp.sh` push guards and flags, `build-platforms.sh` and the `package.mjs` clean) against shimmed `ssh`/`rsync`/`curl`/`npm`/`php`/`mv`/`sleep` and a sandbox host tree (docroot with the public link and `.taskmind/`, protected tree with `releases/`) with restrictive source modes: dry run, host and `--prod` guards, payload deny/allow-list, lint-before-flip, per-release stamp verification through the `X-TaskMind-Release` header with a simulated PHP cache lag, a stuck or missing header, a request with no answer asked again and the one 150 s window, the `Require all denied` release store and its direct-URL refusal, automatic rollback with compare-and-swap, first-install unwind of the link, the deploy lock, injected failures per phase, data-directory and php pre-checks, rollback, prune across both trees, `--quick` and its gates, rsync `--chmod`, the rollback guard on the data's store version (`workspace.version` against `lib/store-version.txt`), dtp's order (deploy, tag and push, then the device builds, with what is owed; which builds a lane names), and `build-platforms.sh` against shimmed `cargo`, `npm`, `xcrun`, `adb`, `emulator` and `aapt` (both default phones, `IOS_PHONES`, a phone offline or locked skipped and owed, `--ios --debug` refused, the Mac `--debug` bundle built and nothing installed, the Android project regenerated with TaskMind's icons, a RELEASE APK built for the device's ABI, aligned, signed with the local release key and verified before it is installed (never the unsigned or a debug APK), the key made once under `~/.config/taskmind` of the fake home (0600 files in a 0700 directory, the password in no command line or output), reused unchanged by the next run, half a key (either file alone) refused before anything is built, a failed keytool leaving nothing behind, an APK with another certificate never installed, `INSTALL_FAILED_UPDATE_INCOMPATIBLE` (and only it) uninstalling and installing again, the dry run naming the key's state, a missing NDK, no device or AVD, a failed build or install owed). It also runs the real `index.php` and `api.php` under `php-cgi` against a fake host tree to prove each entrypoint binds to its own lib by directory name and sends the release header on every response. `npm run test:deploy:mutations` breaks each rule once (`MUT_JOBS=n` at a time, default 4) and requires its test to fail; `MUT_ONLY=regex` runs only the mutants whose names match, `MUT_APPLY_ONLY=1` only checks that each mutation applies, and `sh tools/test-deploy.sh --only t_name` runs one test.
- Workspace fixtures exercise filtered reads, private tombstones, moves, role changes, cascade cleanup, stale writes, replay receipts and concurrent edits. The CGI cases exercise JSON and CSRF validation and size limits. Core tests exercise delta merging and rejection across accounts and revisions.
- `npm run test:e2e` (Chromium; `TASKMIND_E2E_PORT` picks the port, default 8871): a `desktop` project (1360x900) and a `phone` project (375x812, touch), both running every spec. `session`: the private API (401 signed out and never cacheable, exactly the session for the owner and the partner, 403 for `outsider` with nothing about the team, GET and POST behind the gate, a wrong password), the shell (a member sees who they are and their role, nothing in any browser storage, no sideways scroll, no zoom; a non-member gets the sign-in page with the reason and no app; signing out; each of the four themes and an unknown one on a rewritten session; a refused or failed first read has its own screen; the open page closes when its session ends or the team drops it, on a fake clock).
- `npm run check:core`: exact-byte comparison of the eight shared files listed for TaskMind in `tools/shared-files.json` (runs `node ../tools/check-shared.mjs --app TaskMind`).
- `cargo test --manifest-path native/src-tauri/Cargo.toml`: native navigation policy tests (the start address, what a page may navigate to, the debug-only local preview on 8870). Builds once, then runs offline from the crate cache.

Covered by a real build, not a test: `sh tools/build-platforms.sh --mac --debug` (the Mac bundle) and `--android --debug` (the APK).

Not covered by any test, and not looked at by eye: the native apps' windows (the shells have only been compiled; the navigation policy is unit-tested), an install onto a phone or an emulator, the iOS build, the Windows installers, a live deploy and the live site's own accounts. Every dtp release does the builds and the deploy.
