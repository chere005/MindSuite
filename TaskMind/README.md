# TaskMind

Private team task app, part of MindSuite. Intended URL: `https://seancheren.com/TaskMind/`. It is the graduation of the interim page at `seancheren.com/taskmind/` (seancheren-site), which keeps running until this app replaces it; [docs/GRADUATION.md](docs/GRADUATION.md) says what is ported and what is next.

The browser interface and the native Tauri shells (macOS, iOS, Android; Windows optional) share one HTTPS application. Only members of the workspace's team can open its API: people who have a seancheren.com account **and** a row in the team, each with a role. No registration or public sharing is added. The contract is the typed `packages/core/src/model.ts`.

The app has a workspace API for projects, tasks, subtasks, assignees, comments, activity, events and team management. The session shell runs on the web and native clients. The workspace views and GitHub sync are tracked in `docs/GRADUATION.md`.

- **Team and roles**: `owner`, `admin`, `member`, `viewer`. The matrix (`MATRIX` in `model.ts`) is the one table the page and the server both answer: viewers open, read and comment; members work on tasks and create projects; owners and admins manage members and rules; only an owner deletes a project, moves ownership or touches an owner. A fresh workspace is the owner as owner and the partner as admin (`taskmind_owners` in the site's server configuration names other seed owners).
- **Private projects** (`visibility: private`): seen by owners, admins, the project's owner and its members, and nobody else. What a viewer may not see is absent, and an id they cannot see is answered like one that does not exist.
- **What runs today**: sign-in through the site's accounts, the team gate on every request, a session reply `{ok, me, role, name, csrf, theme}`, the workspace API, and a shell that shows who is signed in with their role in the viewer's theme (the suite's four: midnight, sage, forest, olive), signs out, and closes at once when the session or the membership ends.

## Development

Requires Node 24+, PHP 8.2+ with OpenSSL and mbstring (and `php-cgi` next to it, for the gate and entrypoint tests), and sibling `seancheren-site` and `CoreMind` checkouts (in a worktree, point at them with `TASKMIND_TEST_SITE_LIB=<seancheren-site>/lib` and `COREMIND_REPO=<CoreMind>`). `check:core` compares the shared files that `tools/shared-files.json` lists for TaskMind.

```sh
npm ci
npm test              # typecheck, limits drift, vitest, PHP cases, atomic, staging, deploy harness
npm run build
npx playwright install chromium
npm run test:e2e      # TASKMIND_E2E_PORT=8872 to run beside another checkout
npm run check:core
npm run dev           # TASKMIND_PORT=8872 for another port; default 8870
```

The preview uses disposable accounts and data, never the real site's configuration or data. It prints its localhost address and fixture credentials: `alex` (owner), `sam` (admin) and `outsider` (a site account that is not on the team). The production build contains only public assets/PHP entrypoints and protected application libraries.

## Architecture

`packages/core` holds the typed contract, the access rules, the session screen selection and the in-memory delta merge. It has no DOM, clock or storage. `app/` renders the shell and sends all requests through `api.ts`. `release.ts` and `watch.ts` handle session loss and release changes. `colors.ts` and the CoreMind copy of `theme.ts` provide the theme.

`server/public/TaskMind/api.php` and `index.php` are thin entrypoints over `server/lib`: `taskmind.php` (the team, the gate, the session reply, the release stamp), `store.php` (the encrypted store), `workspace.php` (access, state and deltas), `operations.php` (workspace edits), `error.php` (`RequestError`), `login_limit.php`, `staging.php`, `bootstrap.php`, `atomic.php` (a shared copy, listed in `tools/shared-files.json`) and the generated `limits.php` (`node tools/gen-limits.mjs`; never hand-edit). All of it stays flat in `server/lib` so the deploy audit passes unchanged.

**The gate.** `index.php` and `api.php` call `tm_member()` on every request, before dispatching the request. A signed-out request gets 401, and a site account off the team gets 403. The default GET returns `{ok, me, role, name, csrf, theme}`. The team is read from the encrypted workspace file each time, so removing someone or changing a role takes effect on their next request; nothing is remembered in the session. It fails closed: a workspace that cannot be read admits no one, except that the seed owners get a 503 that says why. Only a fresh install (no `workspace.enc`, and no `workspace.version` or `workspace.v*.enc.bak` saying there ever was one) is seeded: the first request writes the seed team once, under the store's lock, and logs `TaskMind workspace created on first use with the seed team`. An empty, damaged or undecryptable file, one with no `members` list, or a file missing where the marker or a backup remains is never read as "no team yet" (a first write that stopped between the marker and the file needs `workspace.version` removed by hand). The gate is also the only thing the sign-in page asks: signed in but not on the team shows the sign-in form again, with the reason, and no app. The workspace API serves filtered GET snapshots and deltas and accepts CSRF-checked JSON POST operations. [Graduation](docs/GRADUATION.md) describes its request and revision contract.

An open page notices a new release: `api.php` names the release that answered in `X-TaskMind-Release`, `release.ts` compares the stamps, and the session watch (one GET a minute while the tab is visible) reloads the page when the stamp changed. Requests wait 45 s (`REQUEST_TIMEOUT_MS`: a deploy slows the host).

Storage is one AES-256-GCM file outside the web root, `workspace.enc` (plaintext `v: 1`), with its key beside it. Writes serialize through the suite's checked lock/atomic-file helpers (`packages/mind-server/lib/atomic.php`, copied here). After each write `workspace.version` (the number and a newline, readable by group `web`) names the version the file holds, so `deploy.sh` can refuse to point the site at a release that cannot read it; the first write that stores a newer version keeps the old file's exact bytes once as `workspace.v<old>.enc.bak` and refuses to write when a different backup is already there. The encrypted login-attempt ledger (`attempts.enc`) lives beside it.

CoreMind is not a runtime dependency. Eight exact copies are listed in the suite's `tools/shared-files.json`: themes (`app/theme.ts`), atomic storage and its checks (`server/lib/atomic.php`, `server/tools/atomic-test.php`), Tauri `build.rs`, the heavy-build lock, the machine-env loader and its sample, and the tdtp wrapper. AgentSuite is installed through its normal managed installer.

## Privacy

Every API request checks authentication, the site account and the team. The sign-in is rate-limited at this app's endpoint, ten failures per client address and fifteen minutes (the client is the right-most `X-Forwarded-For` entry, because `REMOTE_ADDR` there is the load balancer; the client writes that entry, so this is only a speed bump), plus caps that name no address: ten failures per submitted account name and a hundred for the whole app per hour, refused with the answer of a wrong password and failing closed ([docs/LOGIN-LIMITS.md](docs/LOGIN-LIMITS.md) has the numbers and the denial-of-service price); the existing site's other login endpoints retain their own policy. Responses are non-cacheable, content is rendered as text, and nothing private is written to localStorage, sessionStorage, IndexedDB, the Cache API or a service worker (an e2e test asserts all four are empty).

Encryption is at rest, not end-to-end: the trusted server holds the key. Backups must preserve the protected data directory **and its `.key`**. Missing keys or corrupt ciphertext fail closed rather than becoming an empty team. The native remote page has no Tauri IPC permissions and navigation is limited to the private HTTPS app.

## Native and deployment

`native/` contains the Tauri v2 source and icons for macOS, iOS and Android (Windows installers come from the manual GitHub workflow, which makes a draft private release). `tools/build-platforms.sh` uses the suite heavy-build lock and accepts `--mac`, `--ios`, `--android`, `--windows`, `--dry-run` and `--debug`; with none named it builds the Mac and iOS apps on a Mac.

- **macOS**: builds the app (no dmg: that needs Finder), quits a running copy, replaces `/Applications/TaskMind.app` and reopens it. `--debug` builds a debug bundle in `native/src-tauri/target/debug` and installs nothing.
- **iOS**: the signed device build, installed onto the explicit UDIDs of both phones (the owner's and Person B's, the phones listed in `.local/machine.env`; `IOS_PHONES` replaces the list for one run); it never installs onto every discovered phone, and a phone that is offline or locked is skipped with a warning and listed as owed (not a failed run). SPACE must be mounted (`iOS DeviceSupport`).
- **Android**: `tauri android init` regenerates `gen/android` (ignored), the TaskMind launcher icons replace Tauri's stock ones, and a RELEASE APK is built (unsigned) for the ABI of the attached device or running emulator (an AVD is booted when none is running, as in the suite's other Android lanes), zipaligned, signed with the local release key and verified (`apksigner verify --print-certs` must name `CN=TaskMind, O=seancheren.com`; anything else is never installed), then `adb install`ed and launched; the package and activity are read off the built APK. A device holding a TaskMind signed with another key (the debug-signed builds before this) refuses the update with `INSTALL_FAILED_UPDATE_INCOMPATIBLE`; only that refusal makes the run uninstall that package and install again (the shell keeps nothing but its web login). It is never listed in a store.
  - **The release key** is `~/.config/taskmind/android-release.keystore` (PKCS12, alias `taskmind`, 4096-bit RSA, 100 years) with its generated 40-character password in `android-release.keystore.password` beside it, both 0600 in a 0700 directory, never in the repo; the password reaches keytool and apksigner only as a file, never an argument or output. The first release run makes both, once a device is there to install onto, and says so. One without the other stops the run before anything is built (a new key cannot update the installed app). Back both files up with the machine's other secrets: losing them means uninstalling TaskMind on every device to install it again. `--dry-run` says whether the key exists, would be made, or would be refused. Needs the Android SDK and NDK (`ANDROID_HOME`, default `~/Library/Android/sdk`), a JDK, and the network the first time. `--debug` builds a debug-signed aarch64 APK, makes or reads no release key and touches no device.

`tools/deploy.sh` (test by default; `--prod --yes-prod`; `--dry-run`; `--rollback`) audits `dist/` for account/data/config files, uploads a new release beside the live paths, lints every PHP file on the host, then flips one link:

- Deploy touches only three places (`$PUBLIC_BASE` is `/home/public`, or `/home/public/test` on the test instance): `$PUBLIC_BASE/TaskMind` (the serving symlink), `$PUBLIC_BASE/.taskmind/` (public release directories `<stamp>/`, plus a stable `.htaccess` of exactly `Require all denied`, so direct URLs are refused) and `/home/protected/taskmind[-test]/` (`releases/<stamp>/lib/`, the `previous` stamp file, the lock). Why: Apache answers 403 (`AH00037`) for any symlink whose target is under `/home/protected`, but serves a symlink that stays inside the docroot; so the public code lives under the docroot and only the lib stays protected. There is no `current` pointer.
- `$PUBLIC_BASE/TaskMind` is a symlink with the relative target `.taskmind/<stamp>` (created last on a first install; a real directory or a foreign symlink there aborts, "move it aside"). The flip is one `ln -sfh` + `mv -fh`. `index.php`/`api.php` bind to their own lib by the name of the directory they run from (`basename(__DIR__)` must match `^\d{14}-\d+$`, lib = `/home/protected/taskmind[-test]/releases/<stamp>/lib/bootstrap.php`), so a flip can never pair a new page with an old lib even while PHP still runs a cached old entrypoint. `TASKMIND_LIB_DIR` (local preview, e2e) wins; with neither resolving they answer 503 without naming a path. `api.php` sends `X-TaskMind-Release: <stamp>` on every response (not with `TASKMIND_LIB_DIR`).
- The host stamps each release with its own name (`release.txt`, written during the lint step, never part of the audited payload). Verification: page 200; unauthenticated `api.php` 401 whose `X-TaskMind-Release` equals this release's stamp (any other status is final); `release.txt` = stamp; `build.txt` = version; the direct `/.taskmind/<stamp>/index.php` URL answers 403 or 404. One 150 s window (`VERIFY_WINDOW`) is shared by all these requests: a request with no answer waited 20 s (`CURL_WAIT`) and is asked again, and a value that is still the old release's is asked again once a second, every wait counted against the window. A failed verification rolls back automatically, but only while this run's release is still the one the link names; `previous` is restored to what it was before the failed deploy. A failed **first** install is taken offline again. `--rollback` re-points the link at `previous` and verifies it by its own stamp the same way; it can never remove the only release, and it refuses a release whose `lib/store-version.txt` is missing or lower than the data's `workspace.version` (the build ships `store-version.txt`; it must equal the version `limits.php` reads and writes).
- `/home/protected/taskmind[-test]/previous` is a plain file holding the previous stamp. The newest 5 releases are kept, counted over both trees; the live and previous releases are never pruned.
- One deploy at a time: prepare takes `/home/protected/taskmind[-test]/.deploy.lock` (also taken by `--rollback`) and every way out sends an unlock. A lock older than 30 minutes is reported as stale, with the exact `ssh ... rm -rf` command to clear it; it is never broken automatically.
- Never touched: `/home/protected/taskmind-data[-test]` (web-owned, provisioned separately), the site's `lib[-test]/`.
- Needs beforehand: the site's `lib[-test]/auth.php`, `config.php` and files `auth.php` requires; `/home/protected/taskmind-data[-test]` owned by the SSH user and group `web`, mode 2770 (`mkdir -p DIR && chgrp web DIR && chmod 2770 DIR`). The prepare phase **fails** on both lanes when it is missing or not group-writable, printing those commands. On the test instance, whose sandbox config has no team accounts, `staging-users.json` in the data directory may hold test-only bcrypt hashes for member ids (`staging.php`; production and dev never read it).
- **Lanes**: `dtp` is the fast lane: `tools/deploy.sh --quick` runs `check:core`, `npm test`, the build and the spot e2e (`session.spec.ts`'s private API and member-opens tests, both projects); `tdtp` is `dtp.sh --full`, the same with the whole browser suite. Both fetch `origin/main` first and refuse (before anything is deployed) when origin is ahead or already has the version's tag. Right after the verified deploy they tag and push, then run `tools/build-platforms.sh` (`--web` skips it; `--mac --ios --android --windows` name builds; `--platforms` is Mac, iOS and Android) and report what is still owed. This repo has no remote yet, so a lane stops at the fetch until one is added.
